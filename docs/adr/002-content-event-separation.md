# ADR-002: コンテンツとイベントの分離

| 項目           | 内容       |
| :------------- | :--------- |
| ステータス     | accepted   |
| 決定日         | 2026-11-13 |
| 決定者・承認者 | xzyozi     |
| 置換元ADR      | なし       |

## 1. 背景・課題

- **背景**: 履歴の`sourceId`が`history:{URL}:{訪問時刻}`であり、訪問ごとにドキュメント・チャンク・Embeddingが作られていた。同一URLの関係はどこにも保持されず、URLでの集計は`sourceLocator`の文字列一致に頼っていた。
- **要求・制約**: 月別・トピック別の熱中度（アクセス頻度の推移）を、Embeddingの重複なく算出する。入力データは外部へ送信しない。既存のv1 IndexedDBが存在する。
- **判断しない場合の影響**: 訪問回数に比例してEmbeddingの計算量と保存量が増え続ける。同一URLの熱中度を集計する根拠が文字列一致のままになる。

## 2. 決定

コンテンツ（検索・ベクトル用）とイベント（時系列用）を分離する。

- コンテンツは既存の`SourceDocument`・`MemoryChunk`・`EmbeddingCache`とし、履歴・ブックマークは正規化URLごとに1件とする。
- 訪問・登録・更新は`SourceEvent`として、新設する`events`ストアへ追記する（append-only）。
- 月次集計は`events`を基にし、各Eventの`sourceId`から代表トピックを引いて算出する。
- IndexedDBを`DB_VERSION` 2へ上げる。

個別の決定は次のとおり。現在の仕様は正本（DS・DD）を参照する。

| ID  | 論点                      | 決定                                                                                                           |
| :-- | :------------------------ | :------------------------------------------------------------------------------------------------------------- |
| Q1  | Eventの同一性キー         | `(sourceId, eventType, timestamp)`の複合キー。`put`で冪等化する                                                |
| Q2  | 差分の基準                | Event層は全件`put`。コンテンツ層は`sourceHash`の変化時のみチャンク・Embeddingを再作成。時刻での読み飛ばしなし |
| Q3  | 入力形式・Markdown同一性  | 履歴は訪問ごとに1行を正とする。Markdownは相対パスで同一性を決め、移動・リネームは追跡しない                    |
| Q4  | 本文のないコンテンツ      | Embedding入力は「タイトル + URLのホストとパス」。クエリ文字列は含めない                                        |
| Q5  | `sourceTimestamp`         | 「最終イベント時刻」として残す                                                                                 |
| Q6  | `eventType`               | `updated` / `visited` / `created`の3種類のまま                                                                 |
| Q7  | Event→トピック            | チャンクスコアの合計が最大のトピックを代表とし、Event 1件を代表トピックに1件として数える                      |
| Q8  | 熱中度の重み              | Event件数そのまま。丸めは別Issue #10で検討                                                                     |
| Q9  | v1→v2移行                 | 履歴由来のドキュメント・チャンク・Embeddingを破棄し、`events`を空で作る。Markdown・ブックマークは保持         |
| Q10 | `deleteSource`時のEvent   | Eventはすべて残す                                                                                              |
| Q11 | ドキュメント更新範囲      | DS・DDを更新、BDは責務の分配が変わる範囲のみ。ADRは本書1本。実装前にドキュメントを先に更新                     |
| Q12 | 容量上限                  | 上限・月次集約を設けない                                                                                       |
| Q13 | URL正規化                 | `#fragment`と`utm_*`・`fbclid`・`gclid`を除去、ホスト名を小文字化。その他は維持。元のURLはEventに残す         |

## 3. 理由・代替案

### 採用理由

1. Embeddingはコンテンツ単位で1回だけ計算でき、訪問回数が増えても計算量・保存量が増えない。
2. 訪問を個別のEventとして保持するため、熱中度の推移を回数ベースで再集計できる。集計方法の変更（#10の丸めなど）は保存データに影響しない。
3. 既存の`sourceDocuments`・`chunks`・`embeddings`をそのまま使え、追加するストアは`events`だけで済む。

### 代替案

| 代替案                                 | 利点                           | 欠点・リスク                                                     | 採用しなかった理由                                       |
| :------------------------------------- | :----------------------------- | :--------------------------------------------------------------- | :------------------------------------------------------- |
| 訪問ごとにドキュメントを作る（現状）   | 実装変更がない                 | Embeddingが訪問数分重複する。同一URLの関係を持てない             | 計算量・保存量が訪問数に比例する                         |
| Markdownを内容ハッシュで名寄せする     | 内容不変の移動を追跡できる     | 移動と編集を同時に行うと追跡できない                             | 編集される前提のデータに効果が限定的（Q3）               |
| MarkdownにIDをfrontmatterで埋め込む    | 移動・編集とも確実に追跡できる | 元ファイルを書き換える。書き込み権限が必要                       | 検索用途には過剰で、外部のノートに手を入れてしまう（Q3） |
| v1の履歴をEventへ変換して移行する      | 既存データを再取り込みせず済む | 統合時に残すEmbeddingの判断が増え、移行不具合で元データを壊す恐れ | 履歴は元ファイルから再生成でき、再計算も軽い（Q9）       |
| 同日・同一URLの訪問を保存時に丸める    | 水増しを抑えられる             | 元に戻せない                                                     | 保存は全件、集計時に丸める（#10）                        |

## 4. 影響・トレードオフ

- **利点**: Embeddingの重複計算がなくなる。熱中度の集計方法を、保存データを変えずに見直せる。
- **欠点・コスト**: `events`ストア、v2移行処理、集計処理の改修が必要。Event数は上限なく増える（Q12）。
- **影響を受ける正本文書**: DS（`SourceEvent`、`events`ストア、移行、削除）、DD（Normalizer、MemoryStore、TopicAnalyzer、GraphRenderer）、BD（M-006・M-007の責務）。
- **移行・ロールバック**: v2移行時に履歴由来のデータを削除する。履歴は元のエクスポートファイルから再取り込みするため、ファイルが残っていることが前提。ロールバックはv1のDBを再作成して再取り込みする。
- **既知の制約**:
  - Markdownを移動・リネームすると別ドキュメントになり、旧パスの`updated`イベントが「不明」として残る（Q3・Q10）。
  - 既存のブックマークの`sourceId`が、URL正規化後のURLと異なる場合は、次回の取り込みで別ドキュメントになる。
- **セキュリティ・運用上の影響**: 変更なし。入力データ・URL・Embeddingを外部へ送信しない。
