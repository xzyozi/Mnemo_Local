## 壁打ち項目(全体方針。未決定。推奨回答は叩き台)
子 Issue(#31、#32、#33)に共通する決定をここで扱う。回答はこのコメントへの返信で記録する。

### Q-P1 警告から失敗への引き上げ基準
- **推奨**: 警告で開始し、一定数の PR(目安: 10件)で誤検知0なら失敗へ引き上げる。判断者はリポジトリのオーナー。引き上げの記録は、各子 Issue のコメントに残す。

### Q-P2 ワークフローの統合
現状は `validate-docs.yml`、`validate-mermaid.yml`、`repo-hygiene.yml`、(予定)`pr-guard.yml` と分かれており、ランナー起動(約10〜20秒)が重複する。軽い検査は1秒程度なので、起動時間が支配的になる。
- **推奨**: 当面は分けたままにする。契機(`paths`、PR 専用、push も含む)が異なり、統合すると不要な実行が増える。軽量な検査が増えてきた時点で、「共通の軽量検査」ジョブへの統合を再検討する。
- 考慮点: 統合すると、`paths` フィルタを外す必要があり、Mermaid のような重い検査は分離が必要。

### Q-P3 ローカル実行の入口
開発環境は Windows 中心。CI と同じ検査をコミット前に手元で実行できるようにするか。
- **推奨**: 検査はスクリプト化し(`.github/scripts/`)、CI から呼ぶ。ローカルでの実行手順を `docs/setup/` に書く。Git フック(pre-commit)への組み込みは、初版では行わない。

### Q-P4 ブランチ保護と必須チェック
- **推奨**: 警告運用の期間は必須チェックにしない。失敗へ引き上げた検査から順に、必須チェックへ追加する。`paths` フィルタを持つワークフローは、必須化の前に常時実行へ変更する(skip で pending になるため)。設定変更は GitHub の管理画面で、オーナーが行う。

### Q-P5 派生プロジェクトでの扱い
- **推奨**: 各検査は独立したファイルにし、不要な派生プロジェクトは該当ワークフローを削除するだけで外せる構成にする。削除手順を `docs/setup/` に記載する。

### Q-P6 結果の見せ方
- **推奨**: 警告・エラーは GitHub のアノテーション(`::warning::`、`::error::`)で出し、要約を Job Summary に残す。

### Q-P7 着手順
- **推奨**: #33(規約確定)を先に進める。#31 と #32 は #33 の決定に依存しないため、並行して着手してよい。依存するのは、将来ブランチ名の自動検査を追加する場合だけ。
