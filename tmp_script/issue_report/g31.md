### 調査で分かった前提
- マージは merge commit 方式のため、個々のコミットメッセージが履歴に残る。
- コミット種別の一覧は `.gemini/git.md`(13種)が詳しく、グローバル規約(`project-basics.md`)は4種のみ。機械可読な正本が無い。
- 既存のワークフロー(`validate-docs.yml`、`repo-hygiene.yml`、`validate-mermaid.yml`)は別々で、ランナー起動が重複している。

### Q1 コミット形式の検査対象
PR の全コミット、PR タイトルのみ、のどちらか。
- **推奨**: PR 内の非マージコミットすべて。merge commit 方式で個々のコミットが履歴に残るため。将来 squash に変えるなら、PR タイトル検査へ切り替える。

### Q2 種別一覧の正本の置き場
- **推奨**: ワークフロー(またはスクリプト)内の定数を機械可読な正本とし、`.gemini/git.md` の一覧と同期する。変更時は両方を更新する旨を、スクリプト冒頭のコメントに書く。
- 考慮点: 派生プロジェクトが種別を足す場合の手順。設定ファイル化は初版では過剰。

### Q3 `[WIP]` の扱い
- **推奨**: 形式としては許可するが、マージ対象の PR に `[WIP]` が残っていれば警告する。

### Q4 禁止ファイルの一覧と閾値
- **推奨(案)**: `.env*`(`.env.example`・`.env.sample` を除く)、`*.pem`、`*.key`、`id_rsa*`、`credentials*.json`。サイズは1MB超。例外は allowlist ファイルで指定する。
- 考慮点: 判定は PR で追加・変更されたファイル名とサイズのみ。内容の秘密情報スキャン(gitleaks 等)は #14 で扱う。

### Q5 Issue 紐付けのキーワードと免除
- **推奨**: `Closes`・`Fixes`・`Resolves`・`Refs` + `#番号`。軽微な PR のために、免除ラベル(例: `no-issue`)を用意する。
- 考慮点: 免除ラベルが乱用されないよう、運用は警告のままにして実績を見る。

### Q6 ボット PR の除外
- **推奨**: PR の作成者が `dependabot[bot]` の場合は、コミット形式と Issue 紐付けの検査をスキップする。

### Q7 警告から失敗への引き上げ基準
- **推奨**: 警告で運用し、一定数の PR(目安: 10件)で誤検知がなければ、コミット形式と禁止ファイルは失敗に引き上げる。Issue 紐付けは警告のままにする。
- 考慮点: 引き上げの判断者と時期は、親 Issue #30 で共通方針として決める。

### Q8 実装方式
インラインの bash、`.github/scripts/` のシェルスクリプト、Python 標準ライブラリのどれか。
- **推奨**: `.github/scripts/` に bash スクリプトを置き、ワークフローから呼ぶ。Git for Windows の bash でローカル実行でき、インラインより保守しやすい。
- 考慮点: 開発環境は Windows 中心。Python は `validate_docs.py` で既に使っているが、PR の検査は git コマンドが主なので、シェルが素直。

### Q9 ワークフローの分け方
`pr-guard.yml` を新設するか、`repo-hygiene.yml` に統合するか。
- **推奨**: `pr-guard.yml` を新設する。`repo-hygiene.yml` は push でも動くが、本検査は PR 専用のため。ランナー起動の重複は、親 Issue #30 の統合方針(Q-P2)で再検討する。

### Q10 履歴の取得方法
- **推奨**: `fetch-depth: 0` で全履歴を取得する。小規模リポジトリでは数秒以内で、PR の base と head の差分取得が確実になる。

### Q11 必須チェック(ブランチ保護)にするか
- **推奨**: 初版は必須にしない。警告運用の期間が終わってから、`paths` フィルタなしで常時実行にした上で必須化する(skip で pending になる問題を避ける)。

### Q12 fork からの PR
- **推奨**: `pull_request` トリガー(読み取り権限、シークレット不要)のため、そのまま動く。`pull_request_target` は使わない。
