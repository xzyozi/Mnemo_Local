### 調査で分かった前提
- 規約(`git_flow_and_branch_policy.md`)は `develop` から分岐するとしているが、リモートに `develop` は存在せず、実際の運用は `main` 起点で PR を作成している(PR は `main` 向け)。
- 履歴にあるブランチ名は `docs/…`(PR #20、#24)、`feat/…`(PR #25)、`fix/…`(PR #19)、`core/…`(PR #26、#27、#29)。`hotfix/` の実績は無い。
- Issue 番号を含む名前(`docs/21-…`、`feat/23-…`)と含まない名前(`docs/features-readme`、`fix/dd-delegate-…`)が混在している。
- マージは merge commit 方式(履歴に `Merge pull request #N`)。
- コミット種別は13種(`.gemini/git.md`)。グローバル規約(`project-basics.md`)は4種のみで、差がある。

### Q1 接頭辞の体系
4種+`core/`、コミット種別と一対一(13種)、現状の4種のまま、のどれにするか。
- **推奨**: 4種+`core/`。ブランチは短命で、細かい種別はコミットメッセージが担う。13種にすると `update/` と `fix/` のどちらかで迷う場面が増える。
- 寄せ先(案): `update`・`refactor`・`remake` は `feat/` か `fix/`、`test` は `feat/`、`style`・`clean`・`delete` は変更内容に近い側、`WIP`・`other` は専用接頭辞なし。
- 考慮点: 将来の自動検査は、接頭辞が少ないほど規則が単純になる。

### Q2 `develop` ブランチの扱い
規約の `develop` をどうするか(廃止、任意、必須化)。
- **推奨**: このテンプレートでは `main` 起点を標準とし、`develop` は派生プロジェクトで任意とする。規約の「`develop` へ PR」を書き換え、`hotfix/` の説明も整理する。
- 考慮点: `ci.yml`、`validate-*.yml` は `main`・`develop` の両方を対象にしており、`develop` が無くても動く。

### Q3 命名の基本形と Issue 番号
`<接頭辞>/<Issue番号>-<slug>` を必須にするか。
- **推奨**: Issue 番号は「原則必須」。Issue 起点の運用と一致する。Issue が無い作業(緊急対応、ボット)は例外として許可する。
- 考慮点: 将来のブランチ名検査と、PR と Issue の紐付け(#31)の前提になる。

### Q4 slug の文字種と長さ
- **推奨**: 小文字英数字とハイフンのみ、全体で50文字以内。日本語は使わない(`project-basics.md` の「ブランチ名は英数字とハイフンのみ」と整合)。

### Q5 例外ブランチ
- **推奨**: ボットが作るブランチ(`dependabot/…`)は規約の対象外とする。`hotfix/` は Issue 番号を省略可、ただし事後に Issue を作る。

### Q6 派生プロジェクトでの拡張
派生が接頭辞を追加してよいか。
- **推奨**: 追加可。規約に「基本は5種(feat / fix / docs / hotfix / core)、追加は派生側の文書で定義」と書く。

### Q7 既存ブランチと文書の移行
- **推奨**: 既存のマージ済みブランチは対象外。現在の規約例を新規約へ書き換えるだけで、履歴の書き換えはしない。

### Q8 自動検査の時期
- **推奨**: 規約を確定してから、別 Issue で検査(警告から開始)を検討する。本 Issue は文書変更のみとする。
